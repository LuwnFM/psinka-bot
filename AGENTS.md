# Регламент разработки и генерации Python-кода (AGENTS.md)

Ты выступаешь в роли Senior Python-разработчика. Твоя задача — писать поддерживаемый, типобезопасный и модульный продакшн-код, готовый к командному Code Review.

---

## 1. Архитектура и модульность

### Запрет на «God File» и монолитность
- Один модуль (`.py`-файл) отвечает строго за одну предметную область и не превышает **300–500 строк**.
- Точка входа (`main.py` / `bot.py`) содержит только сборку зависимостей, регистрацию модулей (Cogs/Routers) и запуск цикла событий.

### Чёткое разделение ответственности (без смешивания уровней)
- **Слой представления (`cogs/` или `handlers/`):** только приём событий/команд, проверка прав доступа, вызов сервисов и форматирование ответа пользователю. Никаких SQL-запросов, парсинга Excel/XML и сложной математики внутри обработчиков команд.
- **Слой бизнес-логики (`services/`):** чистые функции и классы без зависимости от фреймворка мессенджера (не передавай объект `interaction` или `message` внутрь парсеров, калькуляторов или AI-роутеров).
- **Слой данных (`repositories/` или `db/`):** все запросы к БД и работа с файловым состоянием изолированы здесь.
- **Конфигурация (`config.py`):** чтение и валидация переменных окружения при старте (через `pydantic-settings` или `dataclasses`), без разбросанных по всему коду вызовов `os.getenv()`.

### Никаких побочных эффектов (Side Effects) при импорте и манки-патчинга
- При импорте модуля не должны выполняться: установка пакетов через `subprocess`/`pip`, сетевые запросы, создание таблиц в БД, чтение тяжёлых файлов или запуск фоновых задач. Вся инициализация переносится в жизненный цикл приложения (`setup_hook` / `on_startup`).
- Запрещён **monkey-patching** (подмена атрибутов или методов чужих библиотек и модулей в рантайме) и переопределение глобальных настроек (например, повторный вызов `logging.basicConfig(..., force=True)` в середине файла).

### Хранение данных и справочников
- Не зашивай большие словари синонимов, карты локаций, промпты и таблицы коэффициентов в `.py`-файлы — выноси их в `data/` (`.json`, `.yaml`, `.xlsx`) и загружай при инициализации сервиса.
- Не пиши самодельные генераторы сложных бинарных форматов (например, ручную сборку ZIP/XML для `.xlsx`) — используй проверенные библиотеки (`openpyxl`, `xlsxwriter`).
- Не храни исторические бэкапы файлов в репозитории (`file_v1.py`, `file_old.py`) — для истории версий существует Git.

## 2. Асинхронность и работа с ресурсами
- **Запрет на блокировку Event Loop:** внутри `async def` нельзя выполнять синхронные запросы к БД, долгую работу с диском и синхронные HTTP-запросы. Используй асинхронные драйверы (`asyncpg`, `SQLAlchemy[asyncio]`, `AsyncOpenAI`, `aiohttp`) либо оборачивай блокирующие вызовы в `await asyncio.to_thread(...)`.
- **Переиспользование клиентов:** не создавай новый экземпляр HTTP- или API-клиента внутри каждого запроса или цикла — создавай сессию/клиент один раз при старте сервиса и закрывай при остановке.
- **Единый роутинг событий:** не регистрируй десятки разрозненных слушателей `on_message` на каждый триггер — используй единый диспетчер или встроенный механизм команд/ког фреймворка.

## 3. Стиль кода, типизация и инструменты качества (Ruff + mypy)
Весь генерируемый код должен без единого замечания проходить проверку линтером **Ruff** и статическим анализатором типов **mypy**:
1. **Порядок импортов (isort / Ruff `I`):** все импорты располагаются строго в самом верху файла и делятся на 3 группы с пустой строкой между ними: стандартная библиотека → сторонние библиотеки → локальные модули проекта.
2. **Современная типизация (Python 3.10+, PEP 484):**
   - Обязательно указывай аннотации типов для всех аргументов и возвращаемых значений функций.
   - Используй встроенные типы (`str | None`, `list[str]`, `dict[str, int]`, `tuple[bool, str]`) вместо устаревших `Optional`, `List`, `Dict`, `Tuple` из модуля `typing`.
3. **Читаемость и декомпозиция:**
   - Максимальная длина строки — **110 символов** (допустимо до 120).
   - Максимальная длина функции — **40–50 строк**. Если функция длиннее или глубина вложенности `if`/`for`/`try` превышает **3 уровня** — разбивай её на небольшие приватные функции с говорящими названиями.
   - Имена всех переменных, функций и аргументов в Python пишутся на английском языке в стиле `snake_case`. Локализованные названия параметров для UI передаются через метаданные декоратора (например, `Param(name="период", ...)`).
4. **Обработка исключений (Ruff `E722`, `BLE001`):**
   - Категорически запрещены «голые» `except:` и молчаливые `except Exception: pass`.
   - Лови конкретные классы исключений и логируй сбой с трассировкой (`logger.error("...", exc_info=True)`).

## 4. Документация и комментарии (PEP 257)
- **Docstrings для навигации:** каждая публичная функция, класс и модуль должны иметь лаконичный `docstring` (в стиле Google Style) с описанием назначения, входных параметров, возвращаемого результата и возможных исключений. Сторонний разработчик должен понимать роль функции без чтения её реализации.
- **Осмысленные комментарии:** комментируй только неочевидные архитектурные решения или обходные пути (отвечай на вопрос «почему?», а не «что делает эта строка?»).
- **Актуальность окружения и зависимостей:** при добавлении новой переменной окружения сразу добавляй её в `.env.example`, а при добавлении новой библиотеки — фиксируй её в `pyproject.toml` / `requirements.txt`.

## 5. Правила генерации и редактирования кода (для ИИ-агента)
- **Никаких заглушек и сокращений:** категорически запрещено оставлять `# TODO: реализовать позже`, `pass`, `...` или вырезать куски файла с пометкой `# остальной код без изменений`. Всегда выдавай полный, готовый к запуску код файла.
- **Актуальный синтаксис библиотек:** используй только современные API указанного стека (например, `Pydantic v2`, `SQLAlchemy 2.0+`, `aiogram 3.x`, `discord.py 2.x`). Не смешивай синтаксис устаревших и новых версий.
- **План перед масштабными изменениями:** если задача затрагивает 3 и более файла, сначала выведи краткое дерево изменений и список шагов, и только затем переходи к написанию кода.

## 6. Безопасность, логирование и отказоустойчивость
- **Запрет на `print()`:** для любого вывода используй только настроенный логгер (`logging` / `structlog`), никогда не оставляй отладочные `print()`.
- **Защита секретов и валидация границ:** никогда не хардкодь токены, пароли и API-ключи в коде. Все внешние данные (ответы API, ввод пользователя, конфиги) валидируй через `Pydantic` или `dataclasses`, не передавай нетипизированные словари `dict` между слоями.
- **Таймауты и сетевая устойчивость:** каждый внешний HTTP/API-запрос обязан иметь явный `timeout` и корректную обработку сетевых таймаутов/ошибок, чтобы сбой стороннего сервиса не вешал бота.
